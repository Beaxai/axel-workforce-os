## 1. DATA MODEL
- New 1:1 `user_profiles` table (keep auth/identity lean rather than widening `users`):
  user_id FK (PK), title, timezone, bio (internal-only), internal_notes (internal-only),
  date_joined (default now), last_login_at (nullable timestamptz — see §1a).
- ROLE-SPECIFIC METADATA goes in a SINGLE `role_metadata jsonb` column on `user_profiles`
  — NOT a sparse column-per-role. This is the explicit decision for fields with no existing
  home (UNDERWRITER carrier affiliation / lines / states / verticals; CSA department /
  territory). Shape per role documented in code comments. If you believe a first-class
  column is warranted instead, STOP and flag it before building — do not decide silently.
- Role-specific data that DOES have a home is COMPOSED at read time, never re-stored:
  - AGENT: agency/DBA, NPN, licenses + states, lines of authority, appointment/EO from
    `agent_registrations`; compliance status from `agent_compliance`; book summary (see §2c).
  - CARRIER/PEO/VENDOR reps: company (org), partnership role, programs serviced.
  - EMPLOYER: linked account (4A), role at company, My Program visibility.
- Avatar = initials + deterministic color. `avatar_url` photo upload stays TODO until file
  storage (S3/R2, decision #1). DO NOT build uploads.

## 2. API (server-enforced; openapi.yaml → Orval/Zod regenerated)

### 2a. Read
- GET `/api/users/:id/profile` — composed payload: identity + org + role badge +
  role-specific section. Internal viewers ALSO get open tasks + active deals + internal_notes
  + bio. Non-internal viewers NEVER receive internal_notes/bio (strip server-side, not in UI).
- GET `/api/users/:id/activity` — paginated slice of `activity_log`.
  DEFINE THE FILTER EXPLICITLY: this returns events the user PERFORMED → `created_by = :id`,
  ordered by created_at desc. STATE THE LIMITATION in the response/docs: activity_log is
  deal-scoped, so non-deal actions (login, profile edits, invites) do NOT appear here. (If
  Curtis wants "events about the user" instead, that's `entity_type='user' AND entity_id=:id`
  — flag it as a separate decision; do not silently merge both.)

### 2b. Write
- PATCH `/api/users/:id/profile` — ADMIN edits any profile incl. role_metadata. A user may
  self-edit ONLY contact fields: phone, mobile (on `users`) + timezone (on `user_profiles`).
  This is a CROSS-TABLE write — make it transactional and route fields explicitly. Role, org,
  credentials, and status self-edit are rejected SERVER-SIDE with 403 (not merely hidden).
  Password changes go through the existing 3.5 reset machinery — no new credential surface.
- POST `/api/users/invite` — wraps 3.5 admin-invite registration (ADMIN-only); creates
  users + org_members + user_profiles in ONE transaction (all-or-nothing).
- PATCH `/api/users/:id/status` — ADMIN deactivate/reactivate. Deactivation blocks login
  (enforced by the 3.5 status gate per §1a) while preserving ALL history. No hard delete.
- Approved agent registration (existing flow) must create user + org_members + user_profiles
  with agency/license data carried over, in one transaction.

### 2c. AGENT book summary — define the join, don't hand-wave
- Specify exactly: how an agent links to deals (confirm the actual FK/path in `deals` —
  audit it; do not assume), WHICH premium field is summed, and over WHAT status set
  (e.g., bound only vs all). Document the chosen definition in code. It's a LIVE aggregate
  (COUNT + SUM) computed per profile view — fine at current scale; do not cache silently.
  Acceptance test 3 verifies it matches the DB under this exact definition.
