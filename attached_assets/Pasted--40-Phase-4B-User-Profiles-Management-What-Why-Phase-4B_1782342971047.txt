# #40 — Phase 4B — User Profiles & Management

## What & Why
Phase 4B (State Document §9) gives every platform user a profile reachable wherever a user appears (avatars, @mentions, task assignees, deal teams, activity feeds), plus an admin user-management surface. Hard dependency on 3.5 (real users, org_members roles, admin-invite registration, password-reset machinery) and 4A (account linkage) — both merged. This is about PLATFORM USERS only; it must NOT merge with 4A account contacts, which stay in the accounts module.

Branch: awf-os-brendy-sprint-1 only. Never touch GitHub main.

## Done looks like
- Each of the 8 seeded users renders a complete, role-correct profile page at /users/:id (AGENT shows agency + license + compliance + book summary; UNDERWRITER shows lines/states/verticals; CSA/ADMIN show department/territory; partner reps show company programs; EMPLOYER shows linked account).
- A single shared mini profile popover appears from every user-avatar site (deal team, activity feed, task assignee, global search) with avatar, name, title, role badge, org, click-to-copy email/phone, and a "View full profile" link.
- /profile lets a user self-edit contact info + timezone + password; role/org/credentials/status are read-only there and rejected server-side if tampered with.
- /admin/users (ADMIN) lists users (name, role, org, status, last login) with invite, edit, and deactivate/reactivate; deactivation blocks login while preserving history.
- Profiles respect relationship-based visibility (an EMPLOYER gets 403 on an unrelated profile), enforced server-side.
- last_login_at updates on login and shows in /admin/users.
- Everything verified in BOTH light and dark; no NEW typecheck errors vs the 3.5 baseline.

## Out of scope
- Avatar photo upload (stays TODO until S3/R2 file storage) — initials + deterministic color only.
- 4A account contacts (separate concept, stays in accounts module).
- Non-avatar AxelTooltip usages — do not blanket-replace; only user-avatar tooltip/hover sites get the new popover.
- A migration-file flow or Supabase (binding decision #1) — schema ships via drizzle-kit push, applying new DDL by direct SQL if the known deals drift blocks push, with the Drizzle files remaining source of truth.

## Steps
1. **Schema — user_profiles (1:1 with users).** New table keyed by user_id: title, timezone, bio (internal-only), internal_notes (internal-only), date_joined, nullable last_login_at, plus a single role_metadata jsonb for fields with no existing home (UNDERWRITER carrier/lines/states/verticals; CSA department/territory). Keep users thin; do NOT add sparse per-role columns. If a field seems to need a first-class column, STOP and flag rather than deciding silently. Net-new schema — flag before building.

2. **Status normalization (treat as an auth-path change).** Canonical status set becomes `active | invited | deactivated` (lowercase). Audited fact: status is currently mixed-case and multi-valued — the table default is `PENDING_APPROVAL` (users.ts), the seed script writes `ACTIVE` (seed-users.ts), and the register handler writes `active` (auth.ts). First grep every reader AND writer of status and the literal PENDING_APPROVAL across api-server (including seed-users.ts) and list them. Then:
   - **Backfill must normalize ALL existing values**, not just one: `ACTIVE`/`active` → `active`, `PENDING_APPROVAL` → `invited`. Confirm the 8 seeded users (currently `ACTIVE`) land on `active`.
   - **Update every writer** so re-seeding/registration can't reintroduce mixed-case drift: the table default, the register handler literal, and seed-users.ts.
   - **Add login-time status gating — this does NOT exist today.** Audited: the 3.5 login handler (auth.ts) gates only on password validity + assigned role; it does not check status at all. Add a check that rejects non-`active` users, and decide explicitly whether `invited` may log in. This is NEW gating in the auth path — review it as an auth-path edit.

3. **last_login_at stamp (auth-path edit).** Add a single UPDATE inside the EXISTING 3.5 login handler to stamp last_login_at; do not add a new auth endpoint.

4. **Read APIs.** GET /api/users/:id/profile returns a composed payload (identity + org + role badge + role-specific section); internal viewers additionally get open tasks + active deals + internal_notes + bio, which are stripped server-side for non-internal viewers. GET /api/users/:id/activity returns a paginated activity_log slice filtered to events the user PERFORMED (created_by = :id), documenting that activity_log is deal-scoped so non-deal actions won't appear.

5. **Write APIs (transactional, server-enforced).** PATCH /api/users/:id/profile: ADMIN edits anything incl. role_metadata; a user self-edits ONLY phone/mobile (users) + timezone (user_profiles) as one cross-table transaction; self-edit of role/org/credentials/status is rejected with 403. POST /api/users/invite wraps the 3.5 admin-invite flow creating users + org_members + user_profiles atomically. PATCH /api/users/:id/status does ADMIN deactivate/reactivate (no hard delete). Approved agent registration must also create user + org_members + user_profiles with agency/license carried over, atomically.

6. **AGENT book summary — define the join.** Audit deals to confirm the actual agent→deal FK/path, the premium field summed, and the status set counted; document the chosen definition in code. Compute as a live COUNT + SUM per profile view (no silent caching).

7. **Record-level authorization.** Add a canViewProfile(viewer, target) helper beyond requireRoles: internal roles see all; AGENT sees internal staff + shared-deal users; EMPLOYER sees only assigned internal staff (403 otherwise); CARRIER/PEO/VENDOR see internal staff + shared-deal profiles. Define "shares a deal" / "assigned internal staff" queries once and reuse on every profile/activity route.

8. **Contract regen.** Add the new paths/schemas to openapi.yaml, run codegen, rebuild libs; never hand-edit generated files.

9. **UI — mini profile popover.** One shared component on ui/hover-card.tsx + ui/avatar.tsx (tokens only) replacing user-avatar tooltip/hover sites in deal team, activity feed, task assignee, and global search — leaving non-avatar tooltips untouched.

10. **UI — profile pages.** /users/:id (identity header, contact block, role-specific section, activity tab; internal viewers also see open tasks + active deals) and /profile (self-edit contact + timezone + password; role/org/credentials/status read-only), both under ProtectedRoute in App.tsx, glass-panel layout.

11. **UI — /admin/users (ADMIN).** Searchable table (name, role, org, status, last login) with invite flow, role-specific field edit, and deactivate/reactivate as glass-card rows.

12. **Verify (acceptance tests).** Run the 9 acceptance tests below; verify every new view in light AND dark; confirm zero NEW typecheck errors vs the 3.5 baseline (do not claim absolute zero — list the baseline). Deliver pass/fail per test.

## Acceptance tests
1. All 8 seeded users render complete, role-correct profiles (AGENT: agency + license + compliance + book summary; UNDERWRITER: lines/states/verticals from role_metadata).
2. Mini popover works from deal avatars, activity feed, task assignee, global search — single shared component; no old AVATAR tooltip remains (non-avatar tooltips untouched).
3. AGENT book summary (count + premium) matches the DB under the Step 6 definition.
4. EMPLOYER GET of an unrelated profile → 403; CARRIER/PEO see only internal + shared-deal profiles — enforced by canViewProfile, server-side.
5. Self-edit: phone/mobile/timezone PATCH persists (cross-table, transactional); self-edit of role/org/status rejected server-side with 403, not merely hidden.
6. ADMIN invite creates users + org_members + user_profiles atomically; approved agent registration produces user + profile with agency/license carried over (atomically).
7. Status migration: backfill normalizes all existing rows to the lowercase canonical set (`ACTIVE`/`active` → `active`, `PENDING_APPROVAL` → `invited`); every status writer updated (table default, register handler, seed-users.ts) so drift can't return; the newly-added login status gate blocks a deactivated user's login with history intact; reactivate restores access; PR lists every status/PENDING_APPROVAL reader AND writer updated.
8. last_login_at updates on login (via the existing handler) and surfaces in /admin/users.
9. Design system honored in BOTH light and dark (tokens, glass recipes, pink/purple); zero NEW typecheck errors vs the 3.5 baseline (baseline listed).

- Auth-path edits: (a) status normalization + backfill + writer updates + **a NEW login-time status gate (none exists today — login currently ignores status)**; (b) last_login_at stamp inside the existing login handler.
- Open decisions surfaced (not invented): activity feed = "performed by user" vs "about user"; role_metadata as jsonb vs first-class columns; book-summary premium definition + deal-link path; whether `invited` users may log in. Confirm before build for a different call.
